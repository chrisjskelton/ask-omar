# Security

Ask Omar 0.1 is experimental. Use the latest release; older snapshots receive no separate security maintenance.

Please report vulnerabilities privately through [GitHub private vulnerability reporting](https://github.com/chrisjskelton/ask-omar/security/advisories/new). Include the affected version, a minimal reproduction using invented data, and the impact. Do not post credentials, personal information, screenshots of private work, or exploit details in a public issue. There is no guaranteed response time for this personal project.

## Trust model

Ask Omar runs as your desktop user. Pi can read files and run commands with that user's permissions. Commands may use the network. Elevation depends on your operating system's authentication and privilege policy.

Pi's native Bash tool is disabled. Model-generated commands can run only through Ask Omar's command tool. The default **Ask First** mode shows the complete command and offers Allow once, Allow for 15 minutes, or Deny. A temporary grant skips approval for routine commands, in the current and later requests, until 15 minutes pass or the conversation ends: New, Stop, a model or safety-mode change, an AI request that fails, times out or is blocked because Pi isn't ready, the idle reset or a service restart. Requests Ask Omar rejects before contacting Pi (for example an over-long question) and the link and web-search shortcuts leave the conversation unchanged. **Ask for Recognized Risks** runs most commands automatically and asks only about risks Omar recognizes, while **Block Commands** removes the command tool (Pi's read-only tools remain). **Always Allow — Dangerous** runs every command without approval. Choosing it in Settings requires a separate confirmation; `ask-omar set-access unrestricted` and editing the config do not.

A command is stopped after 60 seconds or 64 KiB of combined output, and can be up to 32 KiB long. Anything it leaves running in the background is stopped when the conversation ends. Except in Always Allow, Ask Omar requests fresh approval for a small set of clearly high-risk patterns, including recursive forced deletion (`rm -rf`), disk and partition changes, low-level output overwrites, recursively making files world-writable, recursive ownership changes, privilege elevation, host-connected containers, power controls, downloaded code piped into a shell and fork bombs. This is an additional warning gate, not a sandbox or comprehensive shell analysis; equivalent actions can be expressed in ways it does not recognize. Pi's direct read-only tools do not prompt and can access files with your user permissions. Untrusted content can influence an agent; review proposed commands with the same care as commands in a terminal and do not enable Always Allow around untrusted content.

The high-risk prompt is a warning, not a boundary. Approvals travel over the private Unix socket, which any process running as you can reach, including commands Omar was already allowed to run. Once routine commands run without prompting (during a temporary grant, or in Ask for Recognized Risks), a misbehaving model can get around the pattern check, for example by writing and running a script. Ask First without an active grant is the only mode in which every command needs your approval.

Expected boundaries include private local state and Unix-socket access across user accounts, keeping private UI payloads out of process arguments, matching approvals to the pending command, and ending temporary grants after 15 minutes or when the conversation ends. Omar is instructed to treat file and page content as data rather than instructions, but that is a prompt instruction, not an enforced control; only Ask First without an active grant makes you approve every command. Reports about failures of those controls are welcome.

Ask Omar does not implement provider authentication. Pi owns that integration. Provider retention and privacy depend on your chosen provider and account settings. See [privacy and retention](README.md#privacy-and-retention).
